## 개요

Palo Alto Networks Unit 42는 최근 **12~18개월** 사이 소프트웨어 공급망 공격의 규모와 속도가 급격히 변했다고 평가했다. 공격자는 완성된 애플리케이션의 취약점만 찾는 대신, 개발자가 매일 신뢰하고 실행하는 **패키지·IDE 확장·빌드 도구·CI/CD 플러그인**을 노린다.

핵심 변화는 공격 대상이 애플리케이션에서 **애플리케이션을 만드는 디지털 공장**으로 이동했다는 점이다. 개발자 노트북에서 실행된 패키지는 빌드 파이프라인의 자격증명을 훔치고, 탈취한 토큰으로 다른 저장소와 패키지를 오염시킨 뒤, 최종 산출물과 클라우드 런타임까지 영향을 확장할 수 있다.

| 구간 | 주요 노출 | 공격자가 얻는 효과 |
|---|---|---|
| 개발자 엔드포인트 | 패키지 설치 스크립트, IDE 확장, 로컬 자격증명 | 사용자 권한 코드 실행, 키·토큰 탈취, 개발 도구 지속성 |
| CI/CD 파이프라인 | 외부 Action·플러그인·도구, 빌드 메모리, 임시 클라우드 토큰 | 배포 권한 탈취, 빌드 변조, 다른 저장소로 전파 |
| 클라우드 런타임 | 컨테이너 OS 패키지, 시스템 라이브러리, 이미지 기반 계층 | 애플리케이션 스캔 밖의 취약점 악용, 운영 환경 장악 |

## 공급망 공격의 변화

Unit 42는 최근 공격 흐름을 세 가지 사례로 설명한다.

1. **장기적인 메인테이너 신뢰 구축** — XZ Utils 취약점(CVE-2024-3094)처럼 수년에 걸쳐 정상 기여자로 위장한 뒤 핵심 소프트웨어에 백도어 삽입
2. **신뢰 계정 탈취** — Axios 공급망 공격처럼 정상 관리자의 계정을 장악해 인기 라이브러리에 악성 코드를 배포
3. **설치 과정 자체의 무기화** — Shai-Hulud·ChainDrop처럼 패키지 수명주기 스크립트를 이용해 설치 즉시 자격증명을 탈취하고 자동 전파

이 공격들은 정상 저장소, 정상 계정, 정상 패키지 업데이트라는 신뢰 경로를 사용한다. 최종 소스코드나 완성된 바이너리만 검사하면 **빌드 도중 실행됐다가 사라지는 행위**를 놓칠 수 있다.

## ChainDrop — 400개 이상 npm 패키지를 통한 자기 전파

Unit 42가 대표 사례로 든 **ChainDrop**은 `keyv`, `cacheable-request` 등 널리 사용되는 라이브러리를 포함해 **400개가 넘는 npm 패키지**를 감염시킨 자기 전파형 웜이다. 정상 기능을 유지한 채 백그라운드에서 악성 체인을 실행해 개발자가 변화를 알아차리기 어렵게 했다.

### 세 가지 동시 표적

| 표적 | ChainDrop의 행위 | 영향 |
|---|---|---|
| 클라우드 시크릿 | 빌드 서버 메모리의 평문 자격증명·플랫폼 토큰 수집 | 클라우드 및 배포 권한 탈취 |
| 로컬 엔드포인트 | 개발 도구 설정을 변조해 지속성 확보 | 패키지 제거·빌드 종료 후에도 재실행 가능 |
| 패키지 생태계 | 탈취한 npm·GitHub 토큰으로 패키지와 저장소 생성·변조 | 신뢰 관계를 따라 자동 확산 |

ChainDrop의 위험은 개별 악성 패키지 하나가 아니다. 하나의 설치 이벤트가 **개발자 → CI/CD → 패키지 레지스트리 → 다른 개발자**로 이어지는 순환 전파 구조를 만든다는 데 있다.

## SDLC 전 구간의 패키지 가시성

현대 애플리케이션 코드베이스의 **80~90%는 오픈소스 코드**로 구성되며, 단순한 프로젝트도 수천 개의 전이 의존성을 가져올 수 있다. 패키지는 최종 애플리케이션에 포함되는 코드인 동시에 설치 과정에서 개발자와 빌드 서버 위에서 실행되는 프로그램이다.

### 1) 개발자 엔드포인트

개발자는 `npm install`, `pip install`, `cargo build`, `go get`, `mvn install` 등 다양한 설치 명령을 실행하며 동시에 **10~30개의 IDE 확장**을 사용할 수 있다.

웹 브라우저의 콘텐츠는 일반적으로 샌드박스 안에서 실행되지만, 패키지 설치 스크립트와 코드 편집기 확장은 개발자와 동일한 권한을 갖는다. 따라서 악성 또는 탈취된 패키지는 별도 취약점 없이도 다음 작업을 수행할 수 있다.

- SSH 키, 클라우드 자격증명, 패키지 레지스트리 토큰 읽기
- 셸 명령 실행과 추가 페이로드 다운로드
- 소스코드와 내부 인프라 정보 수집
- IDE 작업 설정과 자동 실행 구성 변조
- 자동 업데이트를 통한 악성 버전 배포

### 2) CI/CD 파이프라인

빌드 파이프라인에는 외부 Action, 플러그인, 보안 스캐너, 설치 스크립트와 헬퍼 도구가 연쇄적으로 실행된다. 이 환경은 배포용 자격증명과 임시 클라우드 토큰이 집중돼 있어 공격 가치가 높다.

애플리케이션 패키지 목록인 **SBOM(Software Bill of Materials)** 만으로는 파이프라인에서 실행된 도구를 설명할 수 없다. Unit 42는 빌드 시스템에서 실제로 실행되는 모든 도구를 추적하는 **PBOM(Pipeline Bill of Materials)** 이 함께 필요하다고 강조한다.

| 목록 | 확인 대상 | 놓치기 쉬운 영역 |
|---|---|---|
| 애플리케이션 SBOM | 직접·전이 라이브러리 | 빌드 중 실행 후 산출물에 남지 않는 도구 |
| PBOM | Action, 플러그인, 빌더, 스캐너, 스크립트 | 런타임 이미지 내부 구성 요소 |
| 컨테이너 SBOM | 애플리케이션 + OS 패키지·시스템 라이브러리 | 외부 관리형 서비스와 런타임 동적 의존성 |

### 3) 클라우드 런타임

컨테이너에는 애플리케이션 라이브러리 외에도 OpenSSL 같은 시스템 라이브러리와 OS 도구가 포함된다. 저장소의 애플리케이션 코드가 깨끗하더라도 기반 이미지 계층에 취약한 구성 요소가 남으면 운영 워크로드는 노출된다.

따라서 저장소 스캔 결과만으로 운영 환경의 안전을 판단할 수 없다. 개발자 엔드포인트, 자동화된 파이프라인, 실제 클라우드 워크로드의 텔레메트리를 연결해야 공급망 공격의 이동 경로를 볼 수 있다.

## 왜 빌드 완료 시점의 SBOM만으로 부족한가

SBOM은 어떤 구성 요소가 최종 산출물에 포함됐는지 파악하고 알려진 취약점을 추적하는 데 중요하다. 그러나 **인벤토리 생성 이전에 실행된 악성 행위**는 설명하지 못한다.

예를 들어 악성 `preinstall` 스크립트가 빌드 서버의 토큰을 훔친 뒤 삭제되고 정상 라이브러리만 산출물에 남는다면, 최종 SBOM은 정상적인 패키지 목록을 보여줄 수 있다. 공급망 방어에는 구성 요소의 존재뿐 아니라 다음 정보가 필요하다.

- 어떤 패키지와 도구가 어느 시점에 실행됐는가
- 설치 스크립트가 어떤 프로세스와 네트워크 연결을 생성했는가
- 빌드 중 어떤 시크릿에 접근했는가
- 생성된 산출물의 소스·빌더·의존성을 암호학적으로 증명할 수 있는가
- 개발자 환경의 이벤트와 CI/CD·클라우드 런타임 이벤트가 연결되는가

## 파이프라인 강화 권고

| 통제 영역 | 권고 | 기대 효과 |
|---|---|---|
| 설치 스크립트 | 신뢰하지 않은 패키지는 `--ignore-scripts` 적용 | `preinstall`·`postinstall`을 통한 즉시 코드 실행 차단 |
| 패키지 도입 | 신규 버전에 **cooldown 기간** 적용 | 게시 직후 악성 버전의 조직 내 유입 완화 |
| 의존성 고정 | 버전 범위가 아닌 정확한 버전·커밋 SHA로 고정 | 태그 변경과 예기치 않은 업데이트 방지 |
| CI/CD 네트워크 | 빌드 러너의 외부 통신을 허용 목록으로 제한 | 페이로드 다운로드·시크릿 유출·C2 통신 억제 |
| 빌드 인프라 | 작업마다 폐기되는 임시(ephemeral) 러너 사용 | 지속성 제거와 작업 간 오염 방지 |
| 인증 | 장기 API 키 대신 짧게 유지되는 OIDC 자격증명 사용 | 탈취된 비밀의 재사용 가능 시간 축소 |
| 권한 | 작업·저장소별 최소권한과 환경 승인 적용 | 하나의 토큰으로 여러 패키지·환경이 감염되는 상황 제한 |
| 인벤토리 | SBOM + PBOM + 컨테이너 SBOM 관리 | 개발·빌드·런타임 구성 요소의 사각지대 축소 |
| 프로비넌스 | 커밋·빌드 산출물·SBOM 서명 및 검증 | 소스에서 운영까지 변조 여부와 생성 경로 확인 |
| 통합 탐지 | 엔드포인트·CI/CD·클라우드 텔레메트리 상관분석 | 공급망 전파를 단일 사건으로 식별 |

단기 OIDC는 장기 토큰보다 안전하지만, ChainDrop 사례처럼 **유효한 순간의 메모리에서 탈취되면 악용될 수 있다**. 따라서 토큰 수명 단축만으로 끝내지 않고 대상 저장소·브랜치·워크플로·클라우드 역할에 대한 조건과 최소권한을 함께 적용해야 한다.

## 탐지 관점

이 글은 특정 캠페인의 IoC 목록을 제공하지 않으므로, 정적 차단 목록보다 행위 기반 탐지가 중요하다.

### 개발자 엔드포인트

- 패키지 관리자 자식 프로세스로 `curl`, `wget`, PowerShell, Python, Bun 등이 예기치 않게 실행되는 행위
- 패키지 설치 직후 `.vscode/tasks.json` 등 IDE 자동 실행 설정이 변경되는 행위
- 패키지 설치 프로세스가 SSH·클라우드·npm 설정과 토큰 저장소를 대량으로 읽는 행위
- IDE 확장의 자동 업데이트 직후 새로운 외부 연결이나 셸 실행이 발생하는 행위

### CI/CD

- 빌드 단계에서 러너 프로세스 메모리나 `/proc/<pid>/mem` 접근 시도
- 작업 정의에 없던 외부 호스트·블록체인 RPC 엔드포인트와의 통신
- 일반 빌드 작업에서 npm 패키지 게시, 저장소 생성, 릴리스 수정이 연속 발생하는 행위
- lockfile·패키지 매니페스트 변경 없이 설치 시 새로운 수명주기 스크립트가 실행되는 상황
- 동일 토큰이 짧은 시간 동안 여러 저장소와 패키지에 쓰이는 행위

## IoC 공개 여부

Unit 42의 해당 Insights 페이지에는 **해시, 악성 도메인, IP 주소 또는 악성 URL이 공개되지 않았다.** 따라서 이 게시물의 front matter에는 빈 `iocs` 필드를 만들지 않았다. 원문 기사 주소는 참고문헌이며 침해지표가 아니므로 IoC로 등록하지 않는다.

ChainDrop의 구체적인 지표를 별도로 추가하려면 이 글에서 연결한 ChainDrop 기술 분석 보고서를 독립된 출처로 검토하고, 해당 보고서가 명시적으로 공개한 지표만 별도 게시물 또는 검증된 데이터로 등록해야 한다.

## 시사점

공급망 보안의 경계는 저장소나 완성된 애플리케이션에 머물지 않는다. 패키지는 개발자 시스템에서 실행되고, CI/CD 자격증명에 접근하며, 컨테이너와 클라우드 운영 환경으로 이어진다. 이 중 한 구간만 보호하면 공격자는 다른 신뢰 경로를 이용할 수 있다.

ChainDrop이 보여준 핵심은 **자격증명 탈취와 자기 전파가 하나의 설치 이벤트 안에서 자동화됐다**는 점이다. 공격자는 개별 조직을 하나씩 침해할 필요 없이 개발 생태계의 신뢰 관계를 확산 장치로 사용할 수 있다.

따라서 방어 기준도 “취약한 라이브러리가 포함됐는가”에서 “누가 어떤 도구를 언제 실행했고, 무엇에 접근했으며, 그 결과물을 신뢰할 수 있는가”로 확장돼야 한다. SBOM은 출발점이고, PBOM·컨테이너 SBOM·실행 통제·단기 자격증명·암호학적 프로비넌스·전 구간 텔레메트리 연결이 함께 작동해야 실제 공급망 복원력을 만들 수 있다.
